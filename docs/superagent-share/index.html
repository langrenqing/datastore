Super-agent
面向工程团队的高效交付

从「人盯 Session」到「人做验收」——一条 GitHub issue 的一生

45–60 min 基于 DSH 团队文章与 dsh-superagent 原型

开场只用一句话：今天不聊模型能力，聊「一个人怎么带一个团队规模的 Agent」。全程用一条 issue 贯穿，最后给一个两周能做的试点建议。

导览

今天只回答三个问题

WHY

为什么单任务很强，
团队吞吐还是上不去？

瓶颈从模型能力，转移到了人的注意力。

WHAT

Super-agent 靠哪几条机制同时推进多任务？

四段因果链，不是一张功能清单。

HOW

工程团队怎么低成本试起来，
怎么判断有效？

一条低风险流程、六个度量、两周验证。

主线一条 GitHub issue，从被评论到被合入：Part 1 用它讲痛点，Part 2 用它讲机制，Part 3 用它做 demo。

先亮主线，后面每次讲抽象机制都拉回这条 issue。今天不讲模型训练、prompt 技巧和工具评测。

01

瓶颈不在模型，
在人的注意力。

单任务上限取决于模型能力；多任务上限取决于人能同时关注多少。

这一部分控制在 10 分钟。先把「为什么现在需要新架构」讲透，再进机制。

Why · 痛点

并行度上去了，人却成了调度器

上下文混乱多个会话各说各话，人要在脑子里做合并。
同步阻塞一个会话跑长任务，人只能等，或者切走再切回。
会话割裂任务之间不共享上下文，重复交代背景成为常态。
3–5 个

个人能同时有效关注的 Session 数。这是经验观察，不是测量数据。

「单任务上限取决于模型能力，
多任务上限取决于人的注意力。」—— DSH 团队文章

现场可以做个小调查：你现在同时开着几个 Session？其中几个是真的在推进？

3–5 个是原文里的观察值，讲的时候说「经验上」。可以现场举手，比给一个假精确的数字更有说服力。

Why · 演进

不是替代关系，是两条演进轴

任务内能力目标：把一次任务做深、做稳
ReAct→ 工具调用 / 多 Agent 交接→ Skills
任务间组织目标：让一组任务长期并行
人肉调度→ Personal Agent→ Super-agent
结论多 Agent ≠ Super-agent。前者优化任务内部，后者组织任务之间；Personal Agent 与 Super-agent 也不是替代关系。

Claude Code 那类讨论的是任务内部怎么少交接、少丢信息；DSH 讨论的是一组任务怎么并行推进、让人少操心。用两条轴讲，避免听成「一代取代一代」。

Why · 时机

四个变化，让它从论文变成可跑

01

长上下文可用

跨文件、跨会话携带上下文从演示变成日常。

02

工具与代码执行成熟

读写文件、跑测试、开 PR，闭环能真正走完。

03

推理成本下降

后台多跑几路、投机执行，经济上开始成立。

04

异步运行时与沙箱

非阻塞会话、隔离执行环境，是并行的基础设施。

判断缺任何一项，Super-agent 都只能停留在演示；四项同时成熟，才值得在团队里试。

这一页回答「为什么不是去年」。四个变化缺一不可，尤其异步运行时和沙箱，常被忽略。

Why · 定义

四个词，对应四条机制

连续→Thread / 订阅 / Inline·Spill跨会话保持上下文
高效→Router / Worker 分层 + 过滤后直投同时推进，不互相阻塞
主动→Trigger 事件驱动被环境唤醒，而不是等人开口
持久→计算 / 状态 / 环境分离 + Watchdog换机器、掉容器也能继续
定义Super-agent：打破单任务上下文，跨会话保持上下文，同时推进多项任务。

四个词是原文的四个特点，每一条都对应后面的机制。先给定义，听众后面才有挂靠点。

02

机制是一条因果链，
不是功能清单。

四段：分层隔离 → 事件与上下文 → 交互 → 持久与自愈。每段都回答「解决什么、代价是什么」。

20–25 分钟。四段之间是因果顺序，不是并列功能；每段讲完都回到那条 issue。

What · 分层隔离

Router 负责协调，Worker 负责执行

Router常驻 · 轻量模型 · 与人交互 · 冷启动与跨任务协调
↓
Worker强模型 · 独立上下文
Worker独立目录 · 可 fork subagent
Worker彼此不通信 · 各自推进
关键过滤后的消息直接投给已订阅的 Worker，不经过 Router——这才是 Router 敢用轻量模型、吞吐还能起来的原因。

代价：Worker 之间不共享上下文，靠 Thread、订阅与链式召回补；跨任务取舍仍是 Router 的责任。

先纠正一个常见误解：Router 不是所有消息的必经之路。它只在冷启动和跨任务协调时出现；日常消息由程序按订阅直接投递。

What · 事件驱动

从「推一下动一下」到「环境触发」

Trigger群消息 / PR 评论 / CI 结果 / 邮件
→
程序过滤Fast Path：大多数噪音死在这里
→
语义判断Slow Path：LLM 按策略判断是否行动
→
Thread / 订阅一条 Trigger 是点，一串相关 Trigger 是线
→
Worker已订阅直投；新 Thread 才走 Router
  • 降噪两层：程序层先筛，语义层再判断——成本花在少数值得判断的消息上。
  • 路由两条：新 Thread 由 Router 冷启动；已有订阅的消息程序直投。
注意「Fast / Slow」在原文里有两套含义：过滤的两层、路由的两条。讲的时候要分开，否则听众会绕晕。

这一页是全场的机制核心。先讲过滤，再讲 Thread 与订阅，最后强调 Router 只在冷启动出现；顺手把 Fast/Slow 的两种用法区分开。

What · 上下文

窗口就那么大：Inline、Spill 与链式召回

INLINE

常用信息内联

近期很可能用到的，直接放进窗口，省掉工具往返。

SPILL

低频信息外置

窗口外保留引用或摘要，需要时再按需读回。

CHAIN OF RECALL

顺着 ID 查回去

「昨天那个问题修得怎么样了？」Thread → Worker → PR，沿引用图实时渲染。

SPECULATIVE

后台先试一步

根据环境信号提前执行；有价值就交付，没价值就丢弃，代价是算力。

差别和 OS 换页最大的不同：缺页由内核自动处理；LLM 得自己意识到「我缺什么」，然后再去读。所以同一套机制，换个模型效果可能差很多。

Inline/Spill 用「工作台 + 档案柜」比喻即可，不要展开成分页算法。链式召回用群聊里那句问话举例，比画引用图更直观。投机执行要讲清「没价值就丢弃」，否则听起来像魔法。

What · 多信道交互

异步 ReAct：人不必等 Agent

过去

run() → 阻塞，直到结果返回

现在

start() → 立即返回
继续 loop，随时收新指令

  • 全双工、非阻塞：后台耗时操作不再挡住前台对话。
  • 代价要讲清：乱序、取消、部分结果、状态一致性，都需要额外设计。
  • 现状：DSH 已实现，但未默认开启——它是运行时能力，不是模型能力。

别把异步 ReAct 说成模型升级；它是会话运行时的事。顺便提一句 Claude Code 和 ChatGPT 也有类似能力，只是叫法不同。

What · 持久与自愈

计算、状态、环境分开；再加一只 Watchdog

计算云端容器Agent Loop 跑在可替换的容器里
状态数据库会话记录、任务记录、订阅关系
环境本地 daemonBYOM（Bring Your Own Machine）· 代码 / 工具链
  • 容器挂了换一个，状态还在就能继续；本地环境不动，daemon 只负责执行命令、送回结果。
  • 为什么不把环境搬上云：未提交改动、私有凭据、特定硬件和工具链，搬上去结果就不一样了。
  • 前提是云端与端侧互信：云端一旦被攻破，连着的所有设备都危险。
Watchdog独立 Session、定时消息驱动；看的不只是进程存活，更是 LLM 循环死锁或偏离目标。它自己也要花 token，不能无限开。

存算分离借的是数据库术语，这里实际是计算/状态/环境三者分离，标题写全。BYOM 首次出现给全称。信任前提单独强调，别一带而过。

What · 串起来

把机制串起来：一条 issue 的一生

评论 / 事件人提出请求人
→
过滤 + 研判按策略决定是否接受规则授权
→
Thread + 订阅后续消息自动送达
→
Worker 执行独立会话 / 目录
→
提 PR结果回写原线程
→
review + 合入人工闸门人
看人人只出现在两头：请求、验收；中间靠授权范围与规则。
兜底Watchdog 定时检查死锁 / 偏离目标；订阅让后续讨论不用再 @ 一次。

这条链路就是 Part 3 的 demo 脚本；demo 里会刻意展示一次纠偏。

这一页把前面四段机制串成一条线。强调「人只出现在两头」，这是后面「注意力预算」的伏笔。

03

怎么落到我们团队？

先选一条低风险、高频的流程，用两周证明它值得扩大。

15 分钟，含 demo。重点是试点路径、度量和边界，不铺开讲部署细节。

How · 角色

人做决策与验收，不是点一下「通过」

人保留
  • 目标与优先级：做什么、不做什么
  • 取舍：范围、方案、发布节奏
  • 评审：代码质量与风险是否可接受
  • 对外沟通与责任归属
Agent 承担
  • 分诊、复现、定位
  • 改代码、补测试、跑 CI
  • 提 PR、回写讨论、跟进评论
  • 把「需要人」的事项整理出来
约束review 容量决定自动化上限。review 变成新瓶颈，就是失败——不是成功。

不要说「人只要点通过」。人保留的是判断和责任；Agent 承担的是执行和整理。review 容量是硬约束，先算这个再谈并发。

How · 授权

把「少打扰」做成制度

01 谁能触发

名单 + 规则

只有允许的人、允许的来源、允许的规则能发起工作；机器人消息不授权。

02 什么必须批

人工闸门

合入、发版、对外沟通、权限变更必须人批；分诊、复现、改代码提 PR 可自动。

03 通知预算

少而准

每天几条、怎么聚合、静默时段；只在需要人行动或结果可用时开口。

04 审计

可回溯

触发 → 授权 → 派工 → 结果，每一步留痕；出了问题能定位到哪一环。

原型对应：评估（Eval）决定接不接受，授权（Mandate）限定范围，订阅（Subscription）决定后续消息送给谁。

这页讲制度，不讲技术。重点是「少打扰」不是靠模型自觉，而是靠名单、闸门、预算和审计这四件事。

How · 试点路径

按价值 / 风险排序，不按技术栈

第一步 · 低风险高频

CI 失败分诊、issue 分诊去重

前置：日志与测试结果可读。
看：误报率、人工介入率。

第二步 · 需人评审

小 bug 修复、文档/测试补齐、PR 初评

前置：分支保护、CI、CODEOWNERS。
看：一次通过率、返工轮次。

第三步 · 多信道 / 持久

IM + GitHub 订阅、
Watchdog、存算分离

前置：信任边界、密钥隔离。
看：可用性、单任务成本。

节奏每一步：2 周试点 + 明确 owner + 回滚开关。没达到退出条件，就不进入下一步。

不要按「先做 CI、再做事件、最后 Watchdog」的技术顺序讲，听众会以为是能力清单。按风险和价值的顺序，每一步都有前置条件和退出条件。

How · 度量

没有这 6 个数，「高效」只是感觉

指标含义示例目标
触发误报率被接受但最终无需行动的比例< 20%
人工介入 / 任务每个任务人出手的次数从 5 降到 2
PR 一次通过率无返工直接合入的比例> 50%
review 返工轮次平均几轮才能合入≤ 1.5 轮
单任务成本token + 容器 + 工具调用设预算上限
首个可用结果时间从触发到 PR / 答复按流程定

先测两周基线，再谈提升；没有基线就只做定性复盘，不要宣称「效率提升」。

目标值是示例，不是承诺。关键是先有基线。没有基线时，只做定性复盘，别拿感觉当数据。

How · 边界

什么时候不该用，坏了怎么办

先排除

  • 短任务、强实时：开一个 Worker 的成本高于人直接做。
  • 不可逆的高风险操作：没有回滚路径，就不该自动。
  • 没有测试与 review 容量的团队：自动化只会放大返工。
  • 没有明确 owner 的流程：出事没人负责。
失败模式护栏
幻觉 / 自信错测试 + 人工闸门
跑飞 / 死循环Watchdog + 预算
权限过大最小权限 + 沙箱
review 变瓶颈限并发 + 分级
成本失控单任务上限 + 熔断
通知轰炸预算 + 聚合
声明dsh-superagent 是研究原型，不是官方产品；部分设计尚未实现。把它当参考实现，而不是可直接投产的软件。

这一页主动说「什么时候不该用」，比只讲优点更能建立信任。原型免责声明要念出来，避免听众误以为已经产品化。

Q & A

大概率会被问到的五个问题

01
成本会不会失控？

单任务预算 + 熔断 + 按流程限额；先测基线再谈优化。

02
代码和凭据出域怎么办？

环境留在本地（BYOM）、最小权限、沙箱、审计；云端与端侧互信是前提。

03
换一个模型还能跑吗？

Inline/Spill 这类机制更依赖模型「知道自己缺什么」，换模型效果会变；要重测。

04
工程师的岗位会怎样？

执行变少、判断变多；review 与架构判断更值钱，不是「不需要人」。

05
和现有 CI / PR 流程冲突吗？

不替代，只是多一个「自动发起 + 自动执行」的参与者；分支保护与 CODEOWNERS 照旧。

答不上来的记下来，会后补数据——比现场编一个强。

这五个是预判，不必逐条念。挑两个现场最可能被问的展开，其余留给 Q&A。

术语表

Trigger环境里的一个不可变事件，如评论、CI 结果。
Thread一串相关 Trigger 组成的上下文线，如一个 PR。
Ticket / 工单一次被授权的工作单元，绑定执行者与渠道。
Router常驻协调层，负责交互、冷启动与跨任务协调。
Worker执行层，独立上下文与目录，可 fork 子 Agent。
Eval / 评估判断一批 Trigger 是否要求新工作，接受或停止。
Mandate / 授权接受工作时授予的范围与强度，不可随意扩大。
Subscription / 订阅工单与线程的关系，决定后续消息送给谁。
Inline / Spill常用信息内联、低频信息外置，只留引用。
Chain of Recall沿对象 ID 引用图逐跳召回上下文。
Speculative Execution后台提前尝试，按结果价值决定交付或丢弃。
BYOMBring Your Own Machine：本地机器作为执行环境接入。
Watchdog独立看门狗 Session，定时介入纠偏与恢复。

术语表是给会后翻阅的，讲的时候不用逐条念；口头上尽量用「触发、线程、工单」这些中文词。

收尾

三个 takeaway，一个 ask

  • 瓶颈是注意力，不是模型。多任务的并行度，最终由人能验收多少决定。
  • 机制是因果链，不是功能清单。分层、事件、交互、持久，四段依次解决四个问题。
  • 先用度量证明，再扩大。两周基线，六个指标，达不到就停。
Ask

选一条低风险、高频的流程，指定 owner，做两周试点；下次评审只看数据，不看演示。

结束在一个具体请求上：不是「大家回去试试」，而是「选一条流程、一个 owner、两周」。这样会议才有下一步。
