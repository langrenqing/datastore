Why · 演进

不是替代关系，是两条演进轴

任务内能力目标：把一次任务做深、做稳
ReAct→ 工具调用 / 多 Agent 交接→ Skills
任务间组织目标：让一组任务长期并行
人肉调度→ Personal Agent→ Super-agent
结论多 Agent ≠ Super-agent。前者优化任务内部，后者组织任务之间；Personal Agent 与 Super-agent 也不是替代关系。

任务内能力解决「一次任务做深」，任务间组织解决「一组任务并行」。Claude Code 那类讨论前者，DSH 讨论后者；避免听成一代取代一代。多 Agent ≠ Super-agent。

没有隔离，事件一多就互相拖垮；没有上下文，事件接不上；没有交互，人还是得等；没有持久，前面都白搭。

这是第二部分的路线图。按顺序问四个问题：同时跑多个任务怎么不互相拖垮（分层）；任务从哪来、上下文怎么接（事件与 Thread）；人怎么插话（异步）；挂了怎么办（分离 + Watchdog）。四段是依赖关系，不是四个并列功能。每讲完一段，回到同一条 issue。

What · 分层隔离

Router 负责协调，Worker 负责执行

Router常驻 · 轻量模型 · 与人交互 · 冷启动与跨任务协调
↓
Worker强模型 · 独立上下文
Worker独立目录 · 可 fork subagent
Worker彼此不通信 · 各自推进
关键过滤后的消息直接投给已订阅的 Worker，不经过 Router——这才是 Router 敢用轻量模型、吞吐还能起来的原因。

代价：Worker 之间不共享上下文，靠 Thread、订阅与链式召回补；跨任务取舍仍是 Router 的责任。

先纠正「所有消息都过 Router」的误解：Router 只做冷启动与跨任务协调，过滤后的消息直接投 Worker。代价是 Worker 之间不共享上下文，靠 Thread 与链式召回补。

What · 事件驱动

从「推一下动一下」到「环境触发」

Trigger评论 / CI / 群消息 → 程序过滤Fast Path → 语义判断Slow Path → 归入 Thread一串事件 → 路由新 / 已订阅
Thread：一串 Trigger 是一条线
T1评论 T2CI 失败 T3review

同一条线共享上下文；一个 Worker 可以同时订阅多条线。

新 Thread Router 冷启动→建 Worker + 订阅
已订阅 程序直投→Worker

只有新任务经过 Router；日常消息直接到执行者。

「Fast / Slow」在原文里有两套含义：过滤的两层、路由的两条；讲的时候分开说。

先讲两层过滤：程序先筛、语义再判；再讲 Thread 是一条线、订阅决定后续消息去哪。两条路由分开讲：新 Thread 走 Router，已订阅直接投。最后提醒 Fast/Slow 有两套含义，别混。

What · 上下文

窗口就那么大：Inline、Spill 与链式召回

上下文窗口 · Inline

手边常用的，直接放进来

当前任务最近消息引用 / 摘要

窗口预算有限，越常用越靠前。

⇄按需读回 / 放回
Spill · 档案柜

低频、完整的信息，留引用

完整日志历史文档旧结果

只留引用，读回时才占窗口。

Chain of Recall
群消息「昨天那个问题…」 → Thread → Worker → PR → 修改记录

每个对象带下一跳的 ID：不靠大记忆库，靠一张可实时渲染的引用图。

差别和 OS 不同：内核自动处理缺页；LLM 得自己意识到缺什么，再去读。
投机后台按环境信号先试；有价值就交付，没价值就丢弃，代价是算力。

用工作台与档案柜比喻 Inline/Spill；强调和 OS 换页的差别——LLM 得自己知道缺什么。链式召回用「群里问一句」的例子；投机执行讲清「没价值就丢弃」。

What · 多信道交互

异步 ReAct：人不必等 Agent

run()：阻塞到结果返回　→　start()：立即返回，继续 loop

同一会话，两条时间线
前台
人：修一下这个→ Agent：收到，在做→ 人：顺便看下另一个→ Agent：好
后台
读代码→ 改→ 跑测试→ 提 PR
回传

代价乱序、取消、部分结果、状态一致性，都要额外设计。
现状DSH 已实现、未默认开启：它是运行时能力，不是模型能力。

run() 阻塞 vs start() 立即返回；两条时间线说明前台对话不被后台任务挡住。代价是乱序、取消、部分结果；现状是 DSH 已实现、未默认开启，说明它是运行时能力，不是模型能力。

What · 持久与自愈

计算、状态、环境分开；再加一只 Watchdog

环境本地 daemonBYOM · 代码 / 工具链
⇄命令 / 结果
计算云端容器Agent Loop · 可替换
⇄读写状态
状态数据库会话 / 任务 / 订阅
Watchdog独立 Session、定时消息驱动；看的不只是进程存活，更是 LLM 循环死锁或偏离目标。它自己也烧 token。
  • 容器挂了换一个，状态还在就能继续；本地环境不动。
  • 环境不搬上云：未提交改动、私有凭据、特定硬件，搬上去结果会变。
前提云端与端侧互信；云端一旦被攻破，连着的所有设备都危险。

环境、计算、状态三者分开：容器挂了换一个、状态还在；本地环境不搬上云的原因要讲透。强调云端与端侧互信是前提。Watchdog 看的是 LLM 死锁或偏离目标，不只是进程存活，而且自己也烧 token。

What · 回顾

四个承诺，四条机制

连续→Thread / 订阅 / Inline·Spill来龙去脉、自动送达、手边与档案柜
高效→Router / Worker 分层 + 过滤后直投协调者与执行者，日常消息不惊动 Router
主动→Trigger 事件驱动评论、CI、群消息都能唤醒
持久→计算 / 状态 / 环境分离 + Watchdog换容器、换机器也能继续
回扣四个承诺不是四个功能，而是四段互相依赖的机制；缺一段，另外三段都会退化。

四个承诺现在都有机制对应：连续靠 Thread 与上下文，高效靠分层与直投，主动靠 Trigger，持久靠三者分离与 Watchdog。强调不是四个功能，而是四段互相依赖；缺一段，另外三段会退化。

How · 角色

人做决策与验收，不是点一下「通过」

人保留
  • 目标与优先级：做什么、不做什么
  • 取舍：范围、方案、发布节奏
  • 评审：代码质量与风险是否可接受
  • 对外沟通与责任归属
Agent 承担
  • 分诊、复现、定位
  • 改代码、补测试、跑 CI
  • 提 PR、回写讨论、跟进评论
  • 把「需要人」的事项整理出来
约束review 容量决定自动化上限。review 变成新瓶颈，就是失败——不是成功。

人保留判断与责任，Agent 承担执行与整理。review 容量决定自动化上限；review 变成新瓶颈，就是失败，不是成功。

How · 授权

把「少打扰」做成制度

01 谁能触发

名单 + 规则

只有允许的人、允许的来源、允许的规则能发起工作；机器人消息不授权。

02 什么必须批

人工闸门

合入、发版、对外沟通、权限变更必须人批；分诊、复现、改代码提 PR 可自动。

03 通知预算

少而准

每天几条、怎么聚合、静默时段；只在需要人行动或结果可用时开口。

04 审计

可回溯

触发 → 授权 → 派工 → 结果，每一步留痕；出了问题能定位到哪一环。

原型对应：评估（Eval）决定接不接受，授权（Mandate）限定范围，订阅（Subscription）决定后续消息送给谁。

把「少打扰」做成制度：谁能触发、什么必须批、通知预算、审计。原型对应评估 Eval、授权 Mandate、订阅 Subscription——制度是「少打扰」的基础，不是靠模型自觉。

How · 边界

什么时候不该用，坏了怎么办

先排除

  • 短任务、强实时：开一个 Worker 的成本高于人直接做。
  • 不可逆的高风险操作：没有回滚路径，就不该自动。
  • 没有测试与 review 容量的团队：自动化只会放大返工。
  • 没有明确 owner 的流程：出事没人负责。
失败模式护栏
幻觉 / 自信错测试 + 人工闸门
跑飞 / 死循环Watchdog + 预算
权限过大最小权限 + 沙箱
review 变瓶颈限并发 + 分级
成本失控单任务上限 + 熔断
通知轰炸预算 + 聚合
声明dsh-superagent 是研究原型，不是官方产品；部分设计尚未实现。把它当参考实现，而不是可直接投产的软件。

主动说什么时候不该用，比只讲优点更能建立信任。失败模式与护栏一一对应；最后念出原型免责声明，避免听众误以为已经可以投产。

Demo（8 分钟）：贴一条评论 → 分诊 → 开 PR（改代码 + 跑测试）→ 人 review（故意展示一次纠偏）→ 合入并回写原线程。三个人工介入点：请求、review、合入。提前录屏兜底，现场失败就放录像；不要为炫技跑复杂任务。

收尾

三个 takeaway，一个 ask

  • 瓶颈是注意力，不是模型。多任务的并行度，最终由人能验收多少决定。
  • 机制是因果链，不是功能清单。分层、事件、交互、持久，四段依次解决四个问题。
  • 先用度量证明，再扩大。两周基线，六个指标，达不到就停。
Ask

选一条低风险、高频的流程，指定 owner，做两周试点；下次评审只看数据，不看演示。

三个 takeaway 各一句话；落到一个明确 ask——一条流程、一个 owner、两周。下次评审只看数据，不看演示。
